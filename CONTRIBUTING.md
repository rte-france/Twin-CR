# Contributing

Welcome! This guide is a **living document** designed to evolve with the project and streamline contributions for everyone. If something is missing or unclear, feel free to propose an update.

All contributors must adhere to our [Code of Conduct](CODE_OF_CONDUCT.md).

---

## Before You Code

- **Discuss major changes first:** Open an issue or discussion before building a large feature or refactoring.
- **Keep PRs focused:** Max 1–2 open PRs per contributor to avoid stale branches.
- **Scope:** 1 PR = 1 single feature or bug fix.

## Git & Branching Rules

- **Target branch:** Always branch from and target `develop` (never `main`).
- **Branch naming:** Use the issue or PR number as a prefix: <ticket-id>_<short-description> (e.g., 1248_matrix_solver). Every branch must directly originate from a tracked work item to ensure end-to-end traceability.
- **Branch ownership:** Each branch is driven by its author. If you want to contribute to an active branch, coordinate with the owner first—no unexpected pushes.
- **Commits:** Conventional format with meaningful context (`type(scope): description`). Keep commits atomic and testable.
- **Developer Certificate of Origin (DCO):** All commits must include a `Signed-off-by: Full Name <email@example.com>` trailer matching the commit author.
  - Add sign-off automatically per commit: `git commit -s` (or configure globally via `git config --global format.signoff true`).
  - Sign off an existing branch: `git rebase --signoff origin/develop`.
- **Merge strategy:** Decided with reviewers. Use _Rebase & Merge_ for clean atomic histories, or _Squash & Merge_ for branches with noisy intermediate iterations.

## Pull Request Checklist

Before submitting a PR:

- [ ] Code builds and passes all tests locally.
- [ ] Non-trivial changes include automated tests.
- [ ] All commits carry a valid DCO `Signed-off-by:` sign-off matching the commit author.
- [ ] Visual changes include screenshots or a quick recording.
- [ ] Intermediate "wip" or "fix typo" commits are cleaned up.

## What We (Probably) Won't Merge

- Non-trivial code changes without tests.
- Giant, uncoordinated refactorings.
- Pure style/formatting PRs that don't change logic or fix a problem.
- Code generated by an AI that the submitter does not fully understand.

## AI Policy

- **Human in the loop:** AI coding assistants are welcome, but you are 100% accountable for the code you submit. You must understand how it works and be able to defend it during review.
- **No autonomous bots:** PRs generated blindly without human review will be closed.
- **PR discussions:** Write your review comments and descriptions yourself—collaborators want to discuss with you, not a model.
